# auth

Who the user is and whether the app is open to them: the account, the session, the app lock.

| Layer             | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | May import                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `domain/`         | `entities/` (`User`, `Session`), `value-objects/` (`EmailAddress`, `Credentials`), `policies/` (`appLock`, `sessionExpiry`), `errors/` (`AuthenticationError`, `BiometricError`)                                                                                                                                                                                                                                                                                                             | `core/domain`, its own files, no package                |
| `application/`    | `ports/` (`AuthSession`, `BiometricGate`, `SessionDataPurger`), `session/` (the session guards and the rules shared by the other features: `requireSession`, `endSession`, `AuthSessionGate` (the `SessionGate` of the core), `purgeCaches`, `AppLock`, `confirmWithBiometrics`, `sessionPolicy`), `use-cases/` (`SignIn`, `SignOut`, `RestoreSession`, `GetCurrentUser`, `EvaluateAppLock`, `UnlockApp`)                                                                                    | `domain`, `core`, its own files, no package             |
| `infrastructure/` | `HttpAuthSession` and its wire class (`dto/sessionDto.ts`), `SessionVault` (the session kept in the secure storage), `biometrics/` (`DeviceBiometricGate` over `ExpoLocalAuthentication`; the text of the prompt comes from outside)                                                                                                                                                                                                                                                         | `domain`, `application`, `core`, the packages it adapts |
| `presentation/`   | `screens/` (`SignInScreen`, `LockScreen`), `components/` (`SignOutDialog`, `SessionNotice`, `RestoreFailure`), `hooks/` (`useSignIn`, `useSignOut`, `useUnlockApp`, `useCurrentUser`), `session/` (`useRestoreSession`, `useSessionCheck`, `useSessionWatch`), `state/` (`accessStore`, the root access state of the app, and `useSessionOpen`), `services/AuthServices.tsx` (the use cases and ports its screens use), `query/sessionQueryKeys.ts`, `i18n/authMessageKeys.ts`, `testIds.ts` | `domain`, `application`, `core`, never `infrastructure` |

- `domain` and `application` are pure: they run in plain Node, with no package.
- The in-memory session and biometric gate of the development build are in `src/composition/dev/in-memory`: they need the simulated server.
- `auth` depends on `core` only. What a session leaves on the device is emptied through the `SessionDataPurger` port: `auth` states the rule and calls the purgers it is given (`purgeCaches`), `meetings` and `documents` implement them (`MeetingCachePurger`, `DocumentCachePurger`), and `src/composition/glue/sessionDataPurgers.ts` makes the list. A feature added later joins that list without `auth` changing.
- The offline policy of the core asks a `SessionGate`; `AuthSessionGate` is the implementation, and the composition hands it to the use cases.
- The app lock and the session expiry are decided here; the check on a timer and on the way back from the background is in `presentation/session`. The state it writes (`accessStore`) is `auth`'s own, and the composition's controller of the session (`src/composition/shell/session`) drives it.
- The text keys, the test ids and the query keys of the screens of `auth` are declared here and joined with the others by the composition (the translation resources, the error catalog).
