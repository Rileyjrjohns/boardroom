# Testing strategy

The pyramid as it exists in this repository, from the cheapest and most numerous tests to the dearest and fewest. The counts are test cases as Jest declares them, taken from a run of each project (`npx jest --selectProjects <project> --json`); they move with every change, so read them as an order of magnitude and regenerate them with that command (`npx jest --listTests | wc -l` counts the files).

| Level                              | Where it runs                           |   Files | Cases | What it proves                                                                                                                                                               |
| ---------------------------------- | --------------------------------------- | ------: | ----: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain and application (`core`)    | Node, no React Native, no Expo          |      60 | 1,064 | The business rules and the use cases, against the in-memory fakes of the ports, and that the fakes keep the contract of the real adapters                                    |
| Adapters and composition (`infra`) | Node, MSW, `node:sqlite`                |      69 | 2,191 | The HTTP, SQLite, file, native-wrapper and in-memory adapters against the same contract suites, and the container end to end in both configurations                          |
| Screens and navigation (`ui`)      | `jest-expo` with Testing Library        |      70 | 2,197 | Components, hooks, screens, the real navigator on the real route files, and the whole app on the real composition root in its mock configuration                             |
| Repository checks (`tooling`)      | Node                                    |      17 | 1,727 | The configuration itself: aliases, route constants, lint rules, `app.config.ts`, the commit hook, the mock API, the shared spec against the code, the links of the documents |
| End to end (Maestro)               | An Android emulator or an iOS simulator | 6 flows |     - | The built app on a device, through the accessibility tree: sign in, vote, vote offline and resync, a confidential document, the lock on resume, the biometric unlock         |

Of those cases, 54 in `core` and 40 in `infra` are shown as skipped on purpose: they are the groups of a contract suite that an adapter cannot take (see below). The numbers say nothing of quality by themselves: what each level does not replace is told in the paragraphs that follow.

**How the levels are kept honest.**

- **Nothing of ours is replaced with `jest.mock`.** The layers are tested against fakes that implement the real ports, and the screens against the real use cases, the real i18n and the real query client (see [The Jest projects in detail](#the-jest-projects-in-detail)). The few `jest.mock` of the repository are in the tests of the thin wrappers of Expo modules (`expo-secure-store`, `expo-sqlite`, `expo-network`, `expo-local-authentication`, `expo-file-system`), on modules that are not ours, each with a comment that says why.
- **The levels overlap on purpose.** A use case is tested alone in `core`, then through a screen in `ui`, then through the real composition root (`rootLayout*.test.tsx`, which render `app/_layout.tsx` and the real route files with `expo-router/testing-library`), and finally on a device by a Maestro flow.
- **The integrated tests and the Maestro flows share their ids.** `src/composition/shell/navigation/rootLayout.voting.test.tsx` (sign in, open `meeting-002`, vote, see it recorded; vote offline and follow the vote in the pending votes), `rootLayout.session.test.tsx` (the lock after the grace period, the unlock, the sign-out from the lock screen), `rootLayout.documents.test.tsx` (a confidential document, protected and watermarked, and its saved copy offline) and `offlineScenario.test.tsx` run the same scenarios as the flows, on the same data of the simulated server and with the same `TEST_IDS`. The flows check that the build does what Jest says it does; Jest checks what a device cannot show quickly (every branch, every language, every failure).

## Contract suites

A port has one behaviour, written once as a suite under the `application/testing/contracts/` folder of the scope that owns the port (`src/core`, `src/features/<feature>`) (`authSessionContract`, `connectivityContract`, `documentCacheContract`, `documentRepositoryContract`, `meetingCacheContract`, `meetingRepositoryContract`, `screenProtectionContract`, `voteOutboxContract`, `voteRepositoryContract`), and run against **every implementation of that port**:

| Contract                                      | Fake (in `core`, `fakes.contracts.test.ts`) | Adapters that run it (in `infra`)                                |
| --------------------------------------------- | :-----------------------------------------: | ---------------------------------------------------------------- |
| Meeting, vote and document repositories       |                     yes                     | In-memory (over the simulated server), HTTP (over MSW)           |
| Authenticated session                         |                     yes                     | In-memory, HTTP                                                  |
| Meeting cache, document cache and vote outbox |                     yes                     | In-memory, SQLite (over `node:sqlite`, with the migrations)      |
| Connectivity                                  |                     yes                     | Simulated, Expo network (over a scripted network state)          |
| Screen protection                             |                     yes                     | In-memory, native wrapper (over a stand-in of the native module) |

A fake is therefore never trusted on its own: what a use-case test learns from `FakeVoteOutbox` is true of `SqliteVoteOutbox` because both pass the same suite. Some groups need a storage that can fail, be closed and opened again, or hold data it cannot read; an implementation without one says so in the options of the suite (`failsStatements`, `survivesReopen`, `holdsUnreadable`) and the group is declared with `describe.skip`, so it shows as skipped instead of silently missing (the 54 and 40 cases above).

## Coverage gate

`npm run test:coverage` measures **every source file of `src/`**, tested or not (`collectCoverageFrom` of `jest.config.js`), so a layer cannot hide behind the files a test happens to import. The test files, the `testing` folders (fakes, builders, contract suites, stubs) and the `.d.ts` are test support or declarations, not production code, and are not counted. Two gates apply, each to statements, branches, functions and lines alike, and `npm run validate` ends with them:

- **90 percent on each `domain` and `application` folder**, of `src/core` and of every feature, each folder on its own (a path entry of `coverageThreshold` per folder, registered as soon as the folder contains source files; a glob would be applied to each file instead);
- **70 percent global**, for the rest. Jest takes the files that have a threshold of their own out of the global figure, so this gate is the bar for the infrastructure, the presentation and the composition together; with both parts above their bar, the whole of `src/` is above 70 percent.

At the time of writing the whole of `src/` is at 98.8 percent of statements, 94.7 of branches, 99.0 of functions and 99.5 of lines. The `domain` folders are at 100 percent on the four measures and the `application` folders together at 99.4, 98.7, 97.8 and 99.5 (the lowest of them, on its own, is 93.8 percent of functions in `src/features/meetings/application`); the lowest figure of the other layers is 92.9 percent of branches in the infrastructure folders. The 90 percent gate is on each folder of the two layers that hold the rules; the 70 percent one is a floor under the adapters and the screens, which are held above it by the contract suites, by the integrated tests above and by the lint rules (the dependency rule, no magic strings, no raw `testID`, no `jest.mock` of our own code), which `npm run validate` runs first. `tooling/` is not under `src/` and is not measured.

**In the CI**, the step "Show the coverage in the run summary" (`if: ${{ !cancelled() }}`, so it also runs when the tests fail) appends a Markdown table to the **summary of the workflow run**, the page of the run on GitHub: one row for the whole of `src/` and one per layer (the `domain`, `application`, `infrastructure` and `presentation` folders of the core and of the features put together, then `src/composition`), with the four measures in percent and the gate of the row (70 for the total, 90 for the domain and the application, none for the others). It is printed by `tooling/printCoverageTable.mjs` from `coverage/coverage-summary.json`, the `json-summary` report of Jest; the table itself is built by a pure function (`tooling/coverageTable.mjs`) that `tooling/coverageTable.test.ts` tests with a fixture, and that test also checks that the gates of the table are those of `jest.config.js`. The full report stays available as the `coverage` artifact of the run. Locally, `node tooling/printCoverageTable.mjs` prints the same table after `npm run test:coverage`.

## Mutation checks

There is no mutation-testing tool in the repository and no mutation score. What is done, by hand, during the reviews, is the check that matters most for a test: break one line of the code under test (take out a guard, change a constant, drop a test id), run the suite, see a test fail for the right reason, put the line back. Those checks of the earlier steps are not recorded in the repository, so none is listed here. For the integrated tests added with the end-to-end flows it was done on a copy of the project, and recorded as what it is, two checks:

- the grace period of the lock (`APP_LOCK_GRACE_PERIOD`) raised from 30 seconds to one hour: the two tests of `rootLayout.session.test.tsx` that expect the lock screen after a long absence fail, and the one that comes back early still passes;
- the test id of the outcome of a cast vote taken off `ResolutionVoting`: the test of `rootLayout.voting.test.tsx` that follows a vote on the real composition root fails (and the flow `login-list-detail-vote.yaml` would, for the same id).

A mutation tool (Stryker) could automate this for `domain` and `application`, where a mutant is cheap to kill; it is not set up, and no claim is made about what it would find.

## End-to-end flows (Maestro)

The flows are in `.maestro/`, written for [Maestro](https://maestro.dev) (a standalone command-line tool, not an npm package, so nothing is added to `package.json` but the scripts). They run **against the mock configuration**: the app starts signed out, the sign-in screen offers the two demo accounts, and a switch simulates being offline (see [Demo controls](design-in-depth.md#demo-controls)). The simulated server is deterministic (`src/composition/dev/in-memory/seed.ts`): `meeting-002` is an upcoming meeting where Alice Martin is a voting member of one open resolution she has not voted on (`meeting-002-resolution-subject`), and `meeting-001` has a confidential report (`meeting-001-document-2`). Every flow starts by **killing the app**, because the simulated server lives in the memory of the JavaScript runtime: a new process is a new server with no vote cast, so the flows do not depend on one another and can run in any order.

| Flow                            | What it does                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `biometric-login-list-document` | Signs in, presses Home, waits 35 seconds (longer than the grace period), brings the app back **without killing it**, asserts the lock screen and no meetings behind it, taps unlock (the biometrics are simulated in the mock configuration), asserts the meetings, opens `meeting-001` and its confidential report `meeting-001-document-2`, and asserts the document screen, the PDF view and the "Protected screen" badge |
| `login-list-detail-vote`        | Signs in with the demo account, opens `meeting-002` from the list, votes "for", reads the confirmation (the choice, "final", and no mention of being offline), confirms, and sees the outcome, the choices gone and the resolution saying the user has voted                                                                                                                                                                 |
| `offline-vote-resync`           | Signs in, opens the meeting, cuts the network with the demo switch, votes, sees "saved on this device" (and nothing yet on the server side), switches back online, and sees the summary of the synchronisation and the resolution saying the user has voted                                                                                                                                                                  |
| `document-watermark`            | Opens the confidential report of `meeting-001`, and asserts the title, the "Protected screen" badge, the PDF view, the absence of an error and, on Android, the watermark with the name and the email of the reader                                                                                                                                                                                                          |
| `document-no-copy`              | iOS only (nothing on Android). Opens the confidential report of `meeting-001`, long-presses the PDF view twice (the middle, then a word of the title) and asserts that no "Copy" or "Copier" menu item shows; then opens the internal agenda of the same meeting and shows that the same gesture does bring it, which is what proves that the first part can see the menu                                                    |
| `lock-on-resume`                | Presses Home, waits 35 seconds (longer than the 30-second grace period), brings the app back **without killing it** (`launchApp` with `stopApp: false`), asserts the lock screen and no meetings behind it, unlocks, and asserts the meetings again                                                                                                                                                                          |

Two of them are the **reference scenarios**, the ones that must always pass, and `.maestro/config.yaml` makes them run first (`executionOrder.flowsOrder`), in this order, before the others:

1. `biometric-login-list-document`: biometric login, the list of the meetings, a confidential document;
2. `offline-vote-resync`: an offline vote, the network back, the outbox synchronised.

Three rules hold for every flow:

- **Ids, not texts.** Everything is selected with `id:` (a `testID`, from `src/core/presentation/testIds.ts`), so the flows do not depend on the language of the device (they were run with the Android emulator in English and the iOS simulator in French). The one text query is the watermark, which asserts the name and the email of the reader: they are data, not translations.
- **A shared sign-in**, `subflows/sign-in.yaml`, which waits for the sign-in screen (up to three minutes: the first start of a development client bundles the JavaScript), taps the demo account and sends the form.
- **Timeouts that mean something.** `extendedWaitUntil` waits for a screen with 30 seconds (the simulated server answers in 400 ms; the rest is a slow emulator) and for a document with 60.

**Installing Maestro** needs Java 17 or later. The official installer puts it in `~/.maestro` and adds it to the `PATH` of your shell profile:

```sh
curl -fsSL "https://get.maestro.mobile.dev" | bash
maestro --version
```

**Running against a development client** (the usual case, since the project uses one). The build must be installed on the emulator or the simulator (`npm run android`, `npm run ios`), and Metro must be running and reachable from it:

```sh
npm start                                  # Metro, in one terminal
adb reverse tcp:8081 tcp:8081              # Android emulator: the device reaches Metro as localhost
npm run e2e:android                        # in another one: all the flows, on the Android device
npm run e2e:ios                            # all the flows, on the booted iOS simulator
npm run e2e                                # an alias of e2e:android
```

The scripts run `maestro --platform <platform> test -e METRO_URL=<url> .maestro`. Environment variables:

| Variable             | Default                 | Meaning                                                                                                                                                                     |
| -------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `METRO_URL`          | `http://localhost:8081` | Where the device reaches Metro (`http://10.0.2.2:8081` on an Android emulator without `adb reverse`). **Set empty, it means a build with no development client**, see below |
| `E2E_ANDROID_DEVICE` | not set                 | The serial of the device (`adb devices`), passed as `--device`. Needed when more than one Android device or emulator is connected                                           |
| `E2E_IOS_DEVICE`     | not set                 | The id of the simulator (`xcrun simctl list devices booted`), passed as `--device`                                                                                          |

The two reference flows, one after the other, by calling the tool directly (Metro running, the development client installed; add `--platform` and `--device` when more than one device is connected):

```sh
maestro test -e METRO_URL=http://localhost:8081 .maestro/biometric-login-list-document.yaml
maestro test -e METRO_URL=http://localhost:8081 .maestro/offline-vote-resync.yaml
```

`npm run e2e:ios` and `npm run e2e:android` run the whole folder, the two reference flows first. Any other flow is run the same way (`.maestro/lock-on-resume.yaml`). `maestro test .maestro` runs the flows at the top of the folder only (`config.yaml` says `flows: ['*.yaml']`, then orders them); the files of `subflows/` are building blocks and are never run alone.

**How the app is opened**, in `subflows/launch.yaml`:

- With `METRO_URL`, `subflows/launch-dev-client.yaml`: it stops the app and opens `exp+boardroom://expo-development-client/?url=<the Metro URL, URL-encoded>&disableOnboarding=1`. The development client does not start the app by itself (it shows its launcher), and the sheet of its developer menu can come up on top of the first screen, which hides the screen from the accessibility tree and makes the flow wait for nothing. The link loads the bundle from Metro and, with `disableOnboarding=1`, keeps the onboarding sheet away. **Do not `clearState` a development client**: it resets the launcher, and the sheet came back after one.
- Without it (`METRO_URL= npm run e2e:android`, or no `-e` at all when calling `maestro` directly), `subflows/launch-app.yaml` calls **`launchApp` directly**, with a clean state. That is the path of a **release or a preview build**, which has no launcher and no Metro. Such a build has to be made with the mock adapters (`EXPO_PUBLIC_BOARDROOM_ADAPTERS=mock`), because a build that is not a development one never guesses the configuration (see [Running against the simulated server](quick-start.md#running-against-the-simulated-server)); the flows need the demo accounts and the demo switch, which only the mock configuration has.
- No default is declared in an `env:` header of a flow, on purpose: in Maestro a value written in a header wins over the one passed with `-e`, so a default there would make `-e METRO_URL=...` unusable.

**Working from a path with spaces.** An Expo build script breaks on a path with spaces (see [iOS scene life cycle](build-setup.md#ios-scene-life-cycle)), and this repository may live in one. The Android run reported below used a copy of the working tree without spaces in its path: `rsync` of the tree to another folder without `/node_modules`, `/android`, `/ios` and `/.expo`, `npm ci`, then `npx expo start --dev-client --port 8081` from there. The flows themselves are in the repository and are run from it.

**What was run.** All four flows passed on an Android 14 emulator (API 34, 1080x2400) with the development client installed and Metro serving the copy described above: first one by one while they were written, then together with `npm run e2e:android`, `4/4 Flows Passed in 2m 13s` (`login-list-detail-vote` 25 s, `offline-vote-resync` 34 s, `document-watermark` 22 s, `lock-on-resume` 52 s, of which 35 are the wait for the grace period). What the run showed, and the flows now account for:

- **A first attempt failed for a reason that is not the app's**: the sheet of the developer menu was on top of the sign-in screen, after a first version of the launch step that called `launchApp` with `clearState` on the development client (see above). The screen was there and Maestro waited three minutes without seeing it, because the sheet is a window of its own. The cause is the reset of the launcher, as far as the next runs showed: with the link alone the sheet did not come back.
- **The watermark is visible to Maestro on Android**, although it is hidden from screen readers (`importantForAccessibility="no-hide-descendants"`): its snapshot lists `document-watermark`, its tiles and their text. The flow asserts the ids and the name and email of the reader. On iOS, XCTest honours `accessibilityElementsHidden` and does not list it: run on a simulator with the guard removed, the flow fails at `assertVisible: document-watermark` (the hierarchy of the screen has the title, the badge, the PDF view and the page indicator, and none of the tiles), so those assertions are guarded with `platform: Android` and the rest of the flow is common. On iOS the watermark is checked on a simulator screenshot instead (see [What was run on iOS](#end-to-end-flows-maestro)). The text of the tiles, their placement above the PDF and `pointerEvents="none"` are also asserted in Jest.
- **The secure window works**: on the document screen `adb screencap` returns no bytes (`FLAG_SECURE`), so the screenshots Maestro takes of that screen are empty.
- A header declared in a flow with `env:` overrides `-e` (see above).

**What was run on iOS.** The four flows passed on an iOS 27 simulator (iPhone 17, Xcode 27.1) with the development client built in place by `npx expo run:ios --device <udid>` (the path of the repository has no space) and Metro on 8081, through `METRO_URL=http://localhost:8081 E2E_IOS_DEVICE=<udid> npm run e2e:ios`: `4/4 Flows Passed in 1m 50s` (`login-list-detail-vote` 20 s, `offline-vote-resync` 21 s, `document-watermark` 18 s, `lock-on-resume` 50 s, of which 35 are the wait for the grace period), and again `4/4 in 1m 48s` after the fix below. No flow needed a change to run on iOS. With `document-no-copy` (iOS only) added, and the text selection cleared by the screen protection module, the five flows passed together: `5/5 Flows Passed in 2m 30s` (`document-no-copy` 37 s, `login-list-detail-vote` 19 s, `offline-vote-resync` 24 s, `document-watermark` 20 s, `lock-on-resume` 50 s). What the run showed:

- **The ids are exposed.** Every id the flows use is an `accessibilityIdentifier` that XCTest sees (sign-in, list, detail, vote dialog, offline banner, sync summary, document screen and badge, PDF view, lock screen); none was missing, so no id was added for the flows.

The choices are now stacked, one button per line, in `ResolutionVoting`, with a test in `MeetingDetailScreen.voting.test.tsx`; the ids did not change.

## The Jest projects in detail

The Jest projects in detail. The pyramid, the contract suites, the coverage gate and the end-to-end flows are above.

Test files are named `*.test.ts(x)` or `*.spec.ts(x)`. Jest runs four projects (`jest.config.js`):

- `core` (the Jest project, not the folder `src/core`) covers the `domain` and `application` folders of the core and of every feature, the test support of those layers and `src/composition/glue`, in a plain Node environment, with no React Native or Expo setup. If either layer reaches for a framework API, its tests fail. Nothing is mocked with `jest.mock`: the use cases are tested against the in-memory fakes of the ports, and the fakes are checked by the contract suites (see [In-memory adapters and contract tests](design-in-depth.md#in-memory-adapters-and-contract-tests)).
- `infra` covers the `infrastructure` folders and `src/composition` apart from its shell (`container`, `persistence`, `device`, `dev`) in a plain node environment, like `core`: the HTTP adapters are tested against MSW, which needs the `fetch`, `Request` and `Response` of Node (the jest-expo preset replaces them with the native ones of Expo), and the SQLite adapters against `node:sqlite`. MSW is ES modules only and Jest 29 runs CommonJS, so this project (and only this one) lets MSW and its dependencies through Babel; `jest.config.js` says how and what to do when MSW adds a dependency. The in-memory, SQLite and HTTP adapters run the contract suites there, and the container is tested end to end in both configurations: the mock one, and the http one over Node's SQLite, the secure storage in memory, the biometrics and the network state scripted, and MSW in front of the simulated server (`createContainer.http.test.ts`: sign in, list, detail, vote, go offline, queue a vote, come back, sync, restart on the same database and find the state again). The six native modules of Expo that the device adapters wrap (`expo-file-system` among them) and the local module ScreenProtection are empty modules there (`NATIVE_MODULES` and one more entry, a `moduleNameMapper` of the project in `jest.config.js`), so the platform factory and the composition root are imported as the app imports them and nothing native is loaded; the tests of the thin wrappers (`ExpoSecureStorage`, `ExpoSqliteOpener`, `ExpoLocalAuthentication`, `ExpoNetworkState`) replace their module with a stand-in of their own, with a comment that says why. `react-native` is a stub there that knows the platform (where the content of the documents lives), and the wrapper of the files is tested against a stand-in of `expo-file-system` that keeps files in memory. It is the one use of `jest.mock` in the repository on a module that is not ours, and there is none on a module of ours.
- `ui` covers the `presentation` folders and the shell of the composition (`src/composition/shell`) on the `jest-expo` preset, with React Native Testing Library. Route files stay thin, and the screens are tested on their own. `src/composition/shell/navigation/rootLayout.test.tsx` renders the real route tree (`app/_layout.tsx` and its routes) with `expo-router/testing-library` and the real composition root behind it, so a root layout that stops mounting a provider fails a test. The i18n stack is never mocked: components are rendered with the real i18next and react-i18next, and a test sets the language through the provider, or, for the device language, by spying on `useLocales` (`src/core/presentation/i18n/testing/setDeviceLanguages.ts`). The session flow is tested through the real navigator and the real route files of `app/` (`src/testing/presentation/renderApp.tsx` replaces only the root layout, with the providers of the tests over the fakes of the ports, and mounts the route files through `tooling/app-routes/`, one re-export per route, because the loader of a directory of the testing library does not skip `app/+native-intent.tsx` the way the router does; `tooling/routes.test.ts` checks that the two directories list the same routes), and the life of the app (background, foreground) is driven by hand (`src/composition/shell/testing/appState.ts`, which stands in for React Native's `AppState`, a stand-in in Jest that listens to nothing). `react-native-pdf` is replaced through `moduleNameMapper` by a stub (`src/features/documents/presentation/testing/reactNativePdfStub.tsx`) that draws a view, records the properties it was given and lets a test report that the file was read, that the page changed or that it failed; only `PdfViewer` imports the package.
- `tooling` covers `tooling/`, in a plain Node environment. It checks the repository itself: the tsconfig aliases match the folders of `src` and the Jest module name mapper, every test file lives under the root of a Jest project (a test that no project would run fails the suite), no test file sits under `app/`, the `commit-msg` hook accepts and rejects the right messages, the lint rules accept and reject the right snippets: the UI code rules, the purity of `domain` and `application`, the imports of test support, and that no restriction is lost when blocks of the configuration overlap (`lint-rules.test.ts`, which lints them with the real configuration through `lint-snippets.mjs`), `app.config.ts` declares the same languages as the source code, the native modules of the real adapters (SQLCipher included) and the Face ID text in each language (`app-config.test.ts`), the environment is read in the root layout only and every variable it reads is in `.env.example` (`environment.test.ts`), the route constants match the files under `app/` (`routes.test.ts`), and `npm run mock:api` starts from the TypeScript sources, answers and stops (`mock-api/main.test.ts`), and serves a device through the real HTTP adapters (`mock-api/server.test.ts`), the code and the shared specification of `docs/spec` list the same things (`spec.test.ts`), and every relative link and anchor of the README and of the documents of `docs/` resolves (`docs.test.ts`, with the helpers of `docsLinks.ts`; the pictures of `docs/media` are checked in a test of their own, which runs once that folder exists).

The fakes of the caches and of the outbox keep copies of the objects they are given and hand back copies, as a real adapter does by turning the data into rows and back; the contract suites check it. What is true of a fake is still not proof for an adapter, which is why every adapter runs the same suites as the fake.

The tests of the screens assert on texts through the translation keys (`t('key')`, `translateCount`) and on roles, never on a sentence copied from a language. The tests that render the real root layout silence the information lines of `ConsoleMonitoring` (the layout builds it with no way to hand it another monitoring), and nothing else of the console. The tests of the screens use real use cases over the application fakes (`createFakes`), the real i18n and the providers of the app (`AppProviders`, with the query client of production, its cache policy included, and the real interface store), through `src/testing/presentation/renderScreen.tsx`. The one thing the helper changes is the delay of the retries, which is zero. They use fake timers: a list batches the update of its rows on a timer, which with real timers lands between two awaits of a test, outside `act`. A query client keeps a timer for every query it holds, which would keep the test process alive: `testing/queryClients.ts` empties the clients of a test when it ends, after the screen is left. Nothing is replaced with `jest.mock`.

Do not put test files under `app/`: expo-router would treat them as routes.

The path aliases are declared once, in the `paths` of `tsconfig.json`. TypeScript, Metro and ESLint read them there, and `jest.config.js` derives its module name mapper from them.

The 90 percent coverage threshold (statements, branches, functions, lines) on each `domain` and `application` folder is registered automatically as soon as the folder contains source files. It is checked by `npm run test:coverage`, which `npm run validate` ends with. The `testing` folders (fakes and builders) are not counted: they are test support.
