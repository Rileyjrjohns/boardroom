# What is not verified

Apart from the screenshot checks of the secure view on one iPhone 17 under iOS 27, nothing of this app has been run on a physical device. What was run, and where:

It proves the logic, not the device                                     |
| Android 14 emulator (API 34), by hand | The app in the mock configuration (the offline switch, voting, the pending votes, the document viewer) and in the http configuration over `npm run mock:api`: a vote queued offline, a cold restart, an unlock with an emulated fingerprint, the vote still waiting, then sent when the connection came back. Beyond that, iOS was not exercised by hand, apart from the Maestro flows below                                                                                                          |

The manual runs were scripted with `adb` and are not part of the repository, so they are evidence for this document and not a regression suite. What is **unverified**, because it needs a device or a platform that was not used:

**The native modules on iOS, and on any physical device**

- That `expo-sqlite` built with SQLCipher on iOS accepts `PRAGMA key` as the opener sends it, answers `PRAGMA cipher_version`, and says "file is not a database" to a wrong key (`unlockDatabase` assumes the documented behaviour and fails closed when it does not hold); on Android the database was opened, closed and opened again. The key-lost path (the unreadable file set aside, the notice to the user) has been run in Jest against stand-ins only, and `deleteDatabaseAsync` rejecting with a message that says "not found" for a database that is not there is assumed (the wrapper tolerates exactly that and lets any other failure go).
- That the iOS keychain stores and returns the items with the options given, that the biometric prompt of iOS shows the text and returns the outcomes the table assumes, that the cancel label and the strong-biometrics option behave as documented on a device, that iOS answers `missing_usage_description` the way the adapter maps it, and that `expo-network` reports `isInternetReachable` and its changes the way the adapter reads them on iOS.
- The screen protection: a physical Android device, and a physical iOS device other than the one iPhone 17 above; the secure view on a screen recording, on mirroring, on any iOS version but 27 (it relies on a private property that may change), and on Android (the Kotlin view compiled and is in the build, and was not run); Android before 14; recording detection on either platform (`recordingStarted` and `recordingStopped` have not been seen); the `UIScreen` fallback of iOS 16; the iOS cover on a scene that resigns active because of a system prompt; that the system posts the screenshot notification on a screenshot of a phone. `FLAG_SECURE` on a React Native `Modal` is not covered, by the design of the flag. See [Native module: ScreenProtection](native-module.md#native-module-screenprotection), which also says what each run showed. Nothing in the TurboModule sketch there was compiled.

**The generated projects and the network**

- That the generated native projects build and run everywhere: `expo prebuild` was run to check the plugins (the SQLCipher flags, the Face ID text in both languages, the permissions, the backup rules), the iOS and Android bundles were exported with Metro, and `expo-doctor` and `expo install --check` pass. Native builds were made from a copy of the project without spaces in its path (an Expo build script breaks on one) and are reported under [iOS scene life cycle](build-setup.md#ios-scene-life-cycle) and [Native module: ScreenProtection](native-module.md#native-module-screenprotection).
- The cleartext rules of the system for the mock API on a real device (see [Running against the mock API](quick-start.md#running-against-the-mock-api)).
- That React Native's `fetch` honours `redirect: 'error'`: the client asks for it on every request, but the networking layer underneath (`NSURLSession`, `OkHttp`) may follow a redirect anyway. If it does, the guarantee that a redirect never carries the token elsewhere is the server's (the API does not redirect), not the client's. And that it gives a readable body stream (`response.body`): where it does not, the client reads the text whole and checks its length after, with the timeout as the bound (the global `fetch` of SDK 57 is the one of `expo/fetch`, which has a stream).

**The document viewer**

- It was run by hand on the Android emulator, and on an iOS 27 simulator through the Maestro flows, where `react-native-pdf` (with `react-native-blob-util`) builds and draws on the New Architecture of SDK 57. The clearing of the text selection of a protected document was run on an iOS 27 simulator only, with synthetic long-presses (see [Native module: ScreenProtection](native-module.md#native-module-screenprotection)): not on a device, not with the handles dragged by a finger, and not on another version of iOS. Unverified on a device: that the viewer reads a `file://` location of the caches directory (iOS) and of the files directory (Android) with spaces or accents in the path, and reports the page it is on; that `expo-file-system` behaves on a device as the stand-in of the tests says (a file moved onto another with `overwrite`, which on iOS removes the target and then renames it, so an app killed between the two leaves a miss and not a half file; `create` over an existing file; listing a directory the system emptied); that the caches directory of iOS and the files directory of Android stay out of the backups as documented; that the global `fetch` of SDK 57 gives a stream for a body of several megabytes, which the download reads in chunks (it falls back on `arrayBuffer` and checks the length after if it does not); and how the watermark lays out with large text, on a tablet and in landscape.

**The screens and the session flow**

- VoiceOver and TalkBack, and large text, on the whole app: the tests check what is asked of the platform (the roles, the state, the live region and the announcement), not what is spoken, and the Maestro flows do not drive them either (they select elements by id, not by what a screen reader would announce). That includes the dialogs (the focus on the title when they open, the content behind unreachable, which on Android rests on `no-hide-descendants` and has been checked in Jest as a flag on the content), the announcements of the outcomes and the banner, and the viewer (the page indicator, the badge, the notice of a capture).
- On iOS: that the biometric prompt makes `AppState` go inactive the way the lifecycle assumes (and that the grace period is not counted from it); that the privacy cover is rendered before the snapshot of the app switcher (it may not be: the native cover of the screen protection closes that gap for protected screens); the native header with its custom actions (`headerRight`) with large text; the autofill of the password managers on the sign-in fields; the keyboard handling of the sign-in form.
- The behaviour of expo-router's protected screens for a link that arrives while the app is already running in the background, on both platforms.

**The pipeline**

- The workflows were not run on GitHub, nothing was run on the servers of Expo (a build, a submission, an update), the Fastlane lanes were not run, and the delivery of an event to a Sentry project and the upload of the source maps were not checked. The [CI/CD](ci-cd.md#cicd) section says what was run instead (the configuration, the validators and the tests of the pipeline files) and what could not be.

**Not built, and so not verified:** certificate pinning, root and jailbreak detection, app attestation, server-side revocation, a real splash screen, the brand artwork and the store identifiers (see [What is not covered](security.md#what-is-not-covered) and [Placeholders in the native configuration](build-setup.md#placeholders-in-the-native-configuration)). No store submission was made.

## What is verified on a device, and what is not

Verified, on an Android 14 emulator and on an iOS 27 simulator (the flows, and what was run, are in [Testing strategy](testing.md#end-to-end-flows-maestro)):

- the four flows of the first runs, against the mock configuration of a development client: sign-in, the list, the detail, a vote online and offline with its synchronisation, a confidential PDF with its badge and its watermark, the lock after the grace period and the unlock;
- the native screen protection (the secure window, the screenshot event, the recreation of the activity), on Android, run earlier with a harness and reported in [Native module: ScreenProtection](native-module.md#native-module-screenprotection);
- on iOS, the same flows except the watermark assertions (the watermark was looked at on a screenshot), with the PDF drawn and the badge shown.

Not verified, and so not claimed:

- **iOS beyond one simulator**: the flows ran on a single simulator (iPhone 17, iOS 27, French), not on another size, on an older iOS, on a phone (apart from the screenshot check of the secure view), or in English; the iOS watermark assertions are left out on purpose (see [Testing strategy](testing.md#end-to-end-flows-maestro)), and the watermark itself was checked on a screenshot, not asserted by a test on the device;
- **a release or a preview build** (`subflows/launch-app.yaml` has not been run: the emulator only has a development client, and `clearState` would reset it);
- **the `http` configuration on a device**: the flows run on the simulated server; the HTTP adapters are tested in `infra` against MSW and the mock API server, never from a phone;
- **the biometric prompt**: the mock configuration recognises the user without showing one, so `lock-on-resume` and `biometric-login-list-document` unlock with a tap; what a system prompt does to `AppState` (see the part on the screens and the session flow, above) is not exercised;
- **the flows in a pipeline**: they need a device and Metro (or a mock build), so they are run by hand with the commands of [Testing strategy](testing.md#end-to-end-flows-maestro); what a pipeline runs of them belongs to [CI/CD](ci-cd.md#cicd).
